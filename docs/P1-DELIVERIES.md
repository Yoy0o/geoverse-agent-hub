# P1：成果版本与逐版验收

0.5.0 将暂停断点、成果版本、验收和实际 Git 合并连成一条流程。日常只读当前结论、与上一版的差异、阻塞项；完整回执和旧版本按需展开。

## 日常操作

1. **开始工作**：读取当前工作摘要和验收标准，显式开工。阶段结论继续写短摘要。
2. **需要切换**：保存暂停原因、当前结论、恢复第一步；有插单则关联其编号。按提示等待或确认 Agent 停止。恢复到待执行后再开工，参见[暂停指南](P1-PAUSE-RESUME.md)。
3. **交付一版**：代码先提交，运行 `task.sh check`，再提交带 `version` 的回执。代码用完整 Git 提交号，文档或实验用可追溯的版本标识。不要填分支名、`HEAD` 或猜测的提交号；`unknown` 不能进入验收。
4. **快速检查**：打开任务的“交付与验收”，看当前版本、结论和上一版差异。需要核实时展开验证、改动清单和交付时的验收标准。差异是回执声明的比较，不是实际 Git diff。
5. **人工验收**：点击“验收当前成果”，重新逐项确认，并确认已核对成果及验证依据。进度中的勾选不会自动带入。缺少绑定检查或仍有风险时，备注须说明实际核对结果和接受理由。明确失败、阻塞、越界或需求变更不能靠备注放行。
6. **实际合并**：Hub 验收通过后，代码项目再运行 `task.sh merge`。脚本在 Git 合并前检查分支提交是否就是已验收版本；不一致则退出，不执行合并。Hub 的“已合并”状态是工作流记录，本身不证明 Git 合并或生产部署。

评审期间新回执、相关检查或任务要求发生变化，会要求重新读取。备注保留，验收勾选重新确认。网络失败不清空评审或粘贴回执的草稿；相同回执通过多个通道重放不会产生重复版本或回滚当前成果。

## 常规示例：室内导航用例修复

第一版回执写“主通道优先已实现，断连用例失败”，版本填写实际提交号，验证如实填 `fail`。这版会保留，但不能验收。

修复后提交第二个提交，运行 `task.sh check`，再提交新回执。页面显示“断连用例 fail → pass”以及改动清单变化。只需核对新变化及仍有效的验收标准，不必重读两次开发过程。验收记录绑定第二版、当时的要求和对应检查；第一版仍可查看。

## 插单示例：导航任务中途处理视频黑屏

暂停导航任务，保存“已完成主通道实验；返回后修复两个断连用例”，关联独立的“Safari 视频黑屏”任务。视频任务使用自己的摘要、版本和验收记录。

视频排查完成后，从插单返回导航断点，恢复到待执行，再显式开工。旧导航执行的迟到回执会归档，不替代新执行成果。若某份归档结果确实有用，可在待执行或待评审时从版本列表查看，明确点击“采用此版作为当前成果”，然后重新验收。任务要求不一致的旧版本不能直接采用。

已结束任务收到的新回执也只归档。需要继续时先“重新打开任务”；需要重新核对原成果时选“重新评审当前版本”。旧验收不会转移到另一版成果。

## Claude、Codex 与脚本

阶段摘要指纹与验收指纹用途不同，不要互换。

| 目的 | MCP | 项目脚本 / REST |
| --- | --- | --- |
| 提交版本 | `submit_receipt`，增加 `version` 和可选 `run` | `POST /api/tasks/:id/receipt` |
| 读取版本和验收依据 | `get_delivery(id, revision?)` | `task.sh delivery <编号>`；`GET /api/tasks/:id/delivery`；末尾加 `/:revision` 查看历史 |
| 验收或退回 | `move_task`，`action=merge/rework` | `task.sh review <编号> review.json`；`POST /api/tasks/:id/review` |
| 显式复用某版 | `select_delivery` | `POST /api/tasks/:id/delivery/:revision/select`，携带当前验收指纹 |
| 上报检查 | 项目脚本调用 REST | `task.sh check <编号>`；`POST /api/tasks/:id/check` |

回执示例，提交前必须替换版本和任务编号：

```text
task: <实际任务编号>
status: done
summary: 主通道优先和两个断连用例已修复
version: <git rev-parse HEAD 得到的完整提交号>
run: <当前执行编号，未知留空>
changed:
  - src/navigation.ts
verify:
  - pnpm test:navigation: pass
scope: ok
risks: 无
```

人工核对后，`review.json` 使用刚读取的成果编号和验收指纹，示例假设共有两项验收标准：

```json
{
  "action": "merge",
  "expectedDeliveryId": "<get_delivery 的 currentId>",
  "expectedFingerprint": "<get_delivery 的 expectedFingerprint>",
  "verificationConfirmed": true,
  "acceptedCriteria": [0, 1],
  "note": "已核对主通道优先与断连用例，结果符合本版要求。"
}
```

`acceptedCriteria` 从 0 开始，必须覆盖本版全部验收标准。Agent 不得自行替用户确认；没有实际核对就不要提交 `verificationConfirmed: true`。遇到 409 重新阅读并核对，不能只换指纹重试。退回使用 `action: rework`，同样绑定当前成果和指纹，并填写原因。

检查可携带 `deliveryId` 明确指定成果；也可通过相同 `version` 和相同任务要求关联。`task.sh check` 上报实际提交号，并检测检查前后的未提交修改及提交变化。有未提交修改的检查不会绑定提交版本，未标版本的旧脚本检查也不会自动成为新版证据。脚本或 Agent 上报的通过结果不代表 Hub 独立执行了测试。

## 保存与升级

- 成果、检查和逐版评审记录保存在任务文档中，随 JSON 备份和同步保留；不依赖默认 90 天的活动日志期限。正常提交不能改写旧快照。管理员恢复备份或删除任务仍会改变这些数据，这不是防篡改审计库。
- 旧回执仍可读，显示为旧记录，不补造提交号、需求快照或已验收状态。首次新交付时保留旧回执，并建立新版。没有交付回执的历史任务仍可按原流程结束，其评审标为未绑定版本。
- 多端同步合并成果、检查和评审事实；不同版本的批准不互相继承。跨端并发修改可能需要重新核对，不自动挑选“已通过”的结果。
- 回执未带执行编号时只能利用当前任务的执行关联，无法完全辨别所有迟到来源。当前正在暂停的执行可以保存收尾回执，但不会恢复任务；更早的执行、恢复后的已取消执行和已结束任务回执只归档，即使任务再次暂停也不覆盖当前成果。
- 升级服务后，更新项目接入包的 `task.sh`、Agent 规则和 runner；保留自己的项目规则。旧客户端直接覆盖 `receipt/review/lastCheck` 等字段会收到冲突提示，应改用上表接口。
- 本批不部署生产；代码合并、发布构建、实际部署和线上核验仍分别处理。通知频率治理、历史成果检索及跨任务复用推荐可作为后续优化。
