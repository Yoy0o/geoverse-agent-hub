# P1：阶段成果自动回传

这是 0.4.0 的首个 P1 切片。P0 的生产发布仍单独待办；本次开发不表示线上已升级。暂停/恢复、成果版本库和提醒治理不在本次实现中。

后续 0.5.0 已补充[暂停/恢复与结构化断点](P1-PAUSE-RESUME.md)；本文保留 0.4.0 的阶段回传约定。

## 日常使用

给 Claude/Codex 的任务要求可以缩短为：

> 接手任务 <编号>，先读取最新工作上下文。有阶段成果时更新同一张短摘要卡，告诉我结论、下一步和需要我决定的事项；最终交付附真实验证依据。

之后在 Hub 的“今日”看决策卡，必要时展开依据。自动回传依赖 Agent 遵循约定并有可用的 MCP 或项目接入包；没有额外的后台模型调用，也不会自动理解任意长聊天记录。

更新项目接入包并核对差异后，应用新的 `AGENTS.md`、`scripts/agent/hub.sh` 等文件；不要覆盖自己维护的项目规则。更新已下载的 `runner.mjs` 并重启执行端。现有任务通过 `task.sh brief <编号>` 刷新任务单。仅升级 Hub 不会更新电脑里旧的脚本和提示词。

网页的“复制任务单”和“创建并复制任务单”使用同一份服务器任务单，包含当前结论和阶段回传约定；有未保存修改时先等待保存。复制失败不会撤销已经创建的任务，可在详情里重试复制。

## 三条回传路径

1. **有 MCP**：先 `get_work_context`，拿到最新 `expectedFingerprint` 和 `content`，再 `update_work_brief`。最终调用 `submit_receipt` 后重新读取上下文，再更新摘要。
2. **有项目脚本**：`bash scripts/agent/hub.sh context` 读取当前绑定任务。把 `{expectedFingerprint, content}` 保存为 JSON，再执行 `bash scripts/agent/hub.sh brief <文件>`。此写入不加入离线自动重试队列；409 必须重新读取和核对变化。
3. **钩子或执行端兜底**：Agent 在阶段回复中输出 `agent-work-brief` JSON 代码块，绑定当前任务并携带指纹。Stop、回复、会话结束和 transcript 通道自动提取；执行端退出时也会补报。

只在有实质结论、阶段验证、阻塞或待决策事项时更新。读文件、心跳、普通进度不产生新摘要。`content` 是完整替换，Agent 应保留仍有效的证据、关联与未决事项。

## 常规工作示例：室内导航方案验证

Agent 读取上下文并运行实验后，提交类似内容（链接为演示占位，实际使用必须替换为真实依据）：

```json
{
  "summary": "主通道优先方案已完成实验；两个断连路段仍需补齐，暂不交付实现。",
  "nextAction": "补齐断连路段并重新运行路径用例。",
  "decision": "首版是否需要跨楼层导航？",
  "recommendation": "首版限定单层，跨楼层另建任务。",
  "risk": "缺少跨楼层连接数据。",
  "evidence": [{ "label": "实验记录", "url": "https://example.com/actual-experiment", "version": "实际实验版本" }],
  "relations": []
}
```

这只更新当前卡片，任务仍在执行；点“已读”不表示同意建议。全部完成后再提交交付回执并进入评审。

## 临时插单示例

原任务的摘要更新为“导航实验已完成，断连用例尚未修复”；下一步写“打开实验记录中的两个失败用例，先补通道交点”。临时问题建独立任务，只有确认关联编号后才填写 `relations`，不要把两个任务的成果写进同一张卡。

0.4.0 阶段摘要只提供上下文。0.5.0 已增加[正式暂停与恢复](P1-PAUSE-RESUME.md)、有效执行计时及[成果版本与逐版验收](P1-DELIVERIES.md)。恢复会话会重新注入当前结论和回传约定。

## 格式与边界

代码块标记使用 `agent-work-brief`；块内为 JSON，包含 `task`、`expectedFingerprint`、`content`。指纹来自刚刚读取的上下文，不能使用文档里的示例值。`content` 字段及长度沿用 `src/focus.js`。

- 单独阶段摘要不改任务状态、验收项、已读进度或决策结果。
- 同一输出同时带摘要和最终回执时，钩子先检查并写摘要，再处理回执；两者分别处理。摘要被拒绝不影响有效回执入库。
- 已写入的相同摘要经第二个通道重放时不再写入。旧报告试图替换不同的新摘要会被拒绝；不进行盲目合并。
- 跨任务、非法链接、缺失或过期指纹不会覆盖卡片。钩子拒绝记录在任务活动中，transcript 响应带 `workBrief.status=rejected`；执行端输出失败原因。直接 REST 返回 400/409，MCP 返回错误。
- 执行端补报入口为 `POST /api/tasks/:id/focus/report`，请求 `{text: "含代码块的输出"}`，沿用现有 Hub 鉴权。接口只更新摘要，不提交回执。
- 不承诺旧摘要自动适配所有后续回执。若新的回执先于对应摘要送达，应重新读取上下文后提交；冲突时保留较新的卡片。

验证重点：跨通道重复上报、摘要与失败回执、过期与跨任务拒绝、恢复会话上下文、脚本冲突反馈，以及真实 workerd 中的相同行为。
