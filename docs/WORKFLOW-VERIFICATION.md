# 数据流验证与本地入口（0.6.1）

日常使用从「今日」读取短摘要和待判断事项；需要复用时进入「成果」，打开具体版本。任务抽屉和成果版本现在能通过地址栏链接直接定位，刷新、重新登录和浏览器前进／后退仍保留位置。

本页区分两种验证：`verify:release` 检查已经部署的版本和读取接口；`verify:workflow` 在独立本地实例上验证写入、状态切换和恢复。后者通过不代表生产实例已经通过验证。

## 本地完整流程

在仓库根目录，使用 Node 22.5+：

```bash
npm ci
npm run verify:workflow
```

命令自行启动仅监听 `127.0.0.1` 的 Hub，使用临时空数据库，完成以下八组检查后退出并清理。它不接受远程地址或既有数据目录，也不会继承生产 Hub、同步、模型或 runner 配置。

| 检查 | 预期结果 |
| --- | --- |
| 隔离与登录 | 空库启动；同步、模型和 OAuth 关闭；未登录访问被拒绝，令牌及网页登录可用 |
| 实时数据 | 创建任务后，SSE 推送同一任务编号 |
| 阶段摘要 | REST 开工、Claude 钩子上报、MCP 读取、Codex 重放共用一份数据；重复上报不重置已读 |
| 插单暂停 | 保存结论和恢复第一步；插单与原任务双向关联；外部执行未确认停止时不能恢复 |
| 恢复执行 | 插单验收后出现恢复提醒；恢复仅到待执行，显式开工生成新执行；旧执行回执只归档 |
| 逐版验收 | 失败回执不能验收；过期版本请求被拒绝；检查与明确确认绑定当前成果 |
| 注意力与复用 | 普通项可延后、批量已读；固定成果引用不继承验收；来源变化重新提醒且不偷换引用 |
| 恢复与持久化 | 导出后清空**脚本自建的样例任务**、恢复，再重启服务；断点、延后、已读、版本、引用和验收记录一致 |

样例中的 GIS／Safari 回执和验收是明确标记的模拟数据，用来验证 Hub 状态机；命令不启动真实 Claude／Codex，不执行业务代码，也不做真实 Git 合并。真实 runner 停止子进程、Git 合并绑定和 Cloudflare 运行时由现有专项测试覆盖。

## 打开可操作的本地样例

```bash
npm run dev:verify
```

运行相同验证后保留实例，默认地址为 **http://127.0.0.1:8789/**。终端会打印每个任务及版本的完整链接，并更新：

- `.local-verification/latest-links.md`：可点击的入口。
- `.local-verification/latest.json`：检查结果、任务链接、数据目录和令牌文件位置。

第一次打开页面，用本机编辑器读取终端所示 `hub-token` 文件，将其中的**样例实例令牌**填入登录框。令牌不放进链接，也不要提交或分享它。登录重载后会回到原链接。

| 本地入口 | 看什么／尝试什么 |
| --- | --- |
| `http://127.0.0.1:8789/?tab=today` | 「跨楼层调研暂停点」的恢复提醒；普通跟踪事项在稍后列表 |
| `http://127.0.0.1:8789/?tab=results` | 已验收的导航、Safari 成果；切换范围查看历史版本 |
| 终端的「常规任务与当前成果」链接 | 导航任务从断连失败到 v2、v3 的版本差异、检查和验收 |
| 「历史版本」链接 | 定位 v2；仅查看，不切换当前 v3，也不自动验收 |
| 「临时插单」链接 | Safari 插单已验收，关联原任务和暂停点 |
| 「等待恢复的断点」链接 | 读取结论和第一步，点击恢复到待执行，再自行开工 |
| 「复用成果的新任务」链接 | 仍是待执行，引用固定 v3；源任务验收不会替代新任务验收 |

通用链接格式为 `/?tab=board&task=<任务编号>&revision=<成果编号>`。`revision` 省略时读取当前成果；这里使用 `D-…` 成果编号，而不是回执里的 Git SHA 或版本名称。链接只在同一个 Hub 实例内有效。任务不存在会明确提示；版本不存在会显示错误，不会用当前版本冒充。

按 Ctrl+C 停止。每次启动创建新的隔离样例库，并重新生成链接；旧样例留在 `.local-verification/hub-workflow-*`，不会导入默认 `data/` 或同步到云端。停止后可以手动删除这些样例目录。该目录已加入 `.gitignore`。

端口占用时可以指定其他端口：

```bash
npm run dev:verify -- --port 8790
```

`127.0.0.1` 指运行命令的电脑；在远程开发环境运行时，不等于你自己电脑的 localhost。远程环境应使用其已有端口转发能力，或在你自己的电脑运行上述命令。

## 已部署实例的只读验证

在已配置 Hub 令牌和 Cloudflare Access 服务凭据的终端运行；不要把凭据粘贴到命令、文档或聊天中。必须指定**实际部署的提交**。例如验证 PR #6 合并提交：

```bash
git fetch origin main
npm run verify:release -- --ref 55980e835884b77f8935234146852715774d9242
```

后续如果部署的就是最新主分支，可以使用：

```bash
npm run verify:release -- --ref origin/main
```

脚本从指定提交读取版本号和七个前端文件的 SHA-256，不要求切回旧分支，也不会误把验证脚本所在新分支当成线上版本。部署构建自身仍须 `dirty=false`。

默认地址取 `wrangler.jsonc` 的 `PUBLIC_URL`；需要检查另一套明确指定的部署时，使用 `--url https://你的Hub域名`。检查包括：

- 健康与能力接口的版本、提交、构建标识、资源指纹，以及实际返回的七个资源。
- 新版注意力队列、三种成果检索范围，以及一个已有任务的生命周期、成果版本读取。空实例明确报告跳过逐任务读取。
- 包含暂停、恢复、版本选择、延后、检索、引用在内的 **13 个工作流 MCP 工具**存在；实际调用四个只读工具检查可用性。

脚本不写样例、不暂停业务任务、不提交回执、不验收、不导入备份；正常读取可能产生访问／工具调用日志。302、401、403、HTML 登录页、缺少工具或版本不一致都会失败。遇到 Access 阻挡，应在已有授权的部署环境完成检查，不能把 HTTP 403 解释为业务功能故障，也不能当作通过。

## 当前边界与后续工作

本次补齐可重复验证、样例隔离、发布读取检查和稳定页面定位。仍需后续跟进：

1. **生产环境验收回执**：在已授权环境执行上述只读验证，记录实际部署提交和结果；本地通过不能替代它。
2. **正式历史数据治理**：旧演示任务的识别、归档和统计排除尚未完成。本命令只保证新验证样例不污染生产。
3. **长时间／多端编辑恢复**：页面刷新后草稿持久化、普通任务字段的多端冲突处理仍需专项改进。
4. **真实使用效果**：用几天真实任务观察待判断项数量、定位旧成果所需时间和恢复任务所需时间，再决定是否需要语义检索或更多自动整理。
