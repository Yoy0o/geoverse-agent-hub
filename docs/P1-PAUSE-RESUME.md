# P1：暂停、恢复与工作断点

0.5.0 新增独立的“已暂停”状态。主动切换工作不再标成“需介入”；后者继续表示确实存在阻塞。这是 PR #4 阶段摘要的后续开发，代码发布与生产部署仍分别验收。

## 网页怎么用

1. 打开待执行、执行中或需介入的任务，点击“保存断点并暂停”。
2. 填写暂停原因、当前结论、恢复后的第一步。有插单时，先单独创建该任务，再选择已有编号。
3. 保存后，任务变为已暂停，保留分支、工作区、已有依据与未决事项。查看停止情况：执行端仍在停止时会显示“等待执行端确认停止”；外部会话需要你在原会话或机器停止 Agent。
4. 插单处理后，从其详情中的“插单处理后可返回”打开原任务。关联插单在 Hub 中结束后，原任务也会进入今日待处理项。
5. 点击“恢复到待执行”。外部执行必须先停止，再勾选确认。恢复后读取第一步，按原来的方式开工或重新派发。

“恢复”只恢复工作安排，不会自动启动 CLI、恢复聊天会话或撤销停止请求。待执行期间不继续累计有效执行时长。Hub 的结束状态不证明 Git 已合并或应用已部署。

暂停草稿可跨页面内实时刷新保留，写入失败不会清空。过期上下文会被拒绝；核对最新结论后重新读取断点表单，避免覆盖另一会话的新成果。

## 常规任务：当天工作结束

仓储导航实验暂告一段落：

- 暂停原因：今天结束，明天继续。
- 当前结论：主通道权重方案已验证；两个断连用例仍失败。
- 恢复第一步：打开现有实验记录，先修复第一个通道交点并重跑失败用例。
- 插单：留空。

明天读取这三行和既有证据后再开始。暂停期间到达的回执仍会保存，但不会自动取消暂停或进入评审；恢复后须核对新回执。

## 临时插单：视频黑屏排查

先创建独立任务“排查 Safari 视频黑屏”，再暂停导航任务并关联这个插单。原任务的第一步仍写导航实验具体该做什么，不把视频排查的过程混入导航结论。

视频排查的详情会显示可以返回的导航任务。插单结束只提示原任务可恢复，由你决定是否继续；系统不会强制切换工作，也不会自动启动另一个 Agent。

## Claude / Codex 与脚本

MCP：`get_work_context` → `pause_task`；恢复时重新读取上下文 → `resume_task` → 确认断点 → `start_task` 或 `dispatch_task`。

`pause_task` 参数为 `id`、`expectedFingerprint`、`reason`、`summary`、`nextAction`，以及可选的 `interruptedBy`。三个文本字段上限依次为 200、280、200 字。插单编号必须存在、尚未结束，不能关联自身或形成循环。

`resume_task` 参数为 `id`、`expectedFingerprint` 和可选的 `confirmedExternalStop`。最后一项只能在确实停止外部 Agent 后填写 `true`，不能用来绕过在线执行端的停止确认。

项目脚本：

```bash
bash scripts/agent/task.sh context <编号>
bash scripts/agent/task.sh pause <编号> pause.json
bash scripts/agent/task.sh context <编号>
bash scripts/agent/task.sh resume <编号> resume.json
```

JSON 文件包含上述对应参数，但无需 `id`，编号由命令传入。指纹必须来自刚读取的上下文。这些操作不进入离线补报队列，也不自动重试冲突。REST 对应 `GET /api/tasks/:id/lifecycle`、`POST /api/tasks/:id/pause` 和 `/resume`。

## 计时和执行边界

- 有效执行时长只累计 Hub 状态为执行中的区间。暂停、待执行、需介入、待评审均不计入；预算提醒使用同一计时。它不是 CPU 用时，也不能证明 Agent 一直在工作。
- 新任务完整记录。旧任务从升级后的首次写入开始记录，并标为部分统计；不把过去跨会话的自然时间推算成真实工时。手填耗时和创建到完成的周期指标保持各自含义。
- 排队任务暂停后不会再被领取。已运行的托管 Agent 收到停止请求后由 runner 终止，并反馈结果；常驻及 `once` 模式都保持心跳，默认检查间隔约 30 秒。离线机器和外部会话无法由 Hub 确认，需要人工检查。
- 已暂停时，开工、派发、普通状态修改和进度上报不能重启执行；迟到钩子不会创建新执行记录。最终回执可保留，但任务仍暂停。
- 恢复到待执行后，迟到消息也不能代替显式开工。带有已取消执行编号的旧回执归档为独立成果版本，不覆盖重新开工后的当前回执与状态。活动摘要遵循日志保留期限，成果版本随任务保存；未携带执行编号的消息无法完整区分来源，接入端应更新脚本并携带编号。
- JSON 备份和同步保留断点与计时。导入到另一台 Hub 时，本地不存在的执行记录按外部执行处理。跨 Hub 的实时停止控制仍应在实际管理该 runner 的 Hub 上进行。
- 当前保留最近一次结构化断点；多次暂停/恢复仍有状态历史和活动记录。本批已补充[成果版本与逐版验收](P1-DELIVERIES.md)，通知频率治理留待后续。

部署新版后，需要更新项目接入包中的 `task.sh`、`AGENTS.md`，以及实际运行的 `runner.mjs` 并重启。先核对差异，保留自己的项目规则。仅升级服务不会替换电脑里旧的脚本。
