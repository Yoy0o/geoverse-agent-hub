# P0 修复、发布验收与下一步

2026-10-29。对应线上演示项目 `工作流演示-20261028`。本轮目标是让新版可发布、保存结果可信；以下发布步骤完成前，不把“代码合并”算作“线上可用”。

## 本轮改动

- 创建任务等待服务器确认后再打开详情。保存期间禁用重复提交；失败及页面内切换都保留表单。同一次失败重试沿用编号，并先检查服务器是否已经保存，避免响应丢失后重复创建或覆盖已有任务。等待时可以切换视图，保存完成不会把人拉回原页面。
- 标题、目标、范围、链接与用量等任务字段在输入时保存到独立草稿中。实时刷新重建输入框也不会丢掉待保存编辑。短暂停止输入后自动保存，失败保留草稿并显示重试。
- 页面显示“保存中 / 已保存 / 未保存”。登录失效后不会悄悄切换成仅页面内保存。
- 版本统一来自 `package.json`。Cloudflare 构建记录提交、构建时间、工作区是否包含未提交改动和关键静态资源哈希；“同步与设置”可查看当前版本。
- `npm run verify:release` 只读检查线上版本、提交、页面与脚本、决策卡接口和 MCP 三个摘要工具。未通过时返回非零状态，不把普通 HTTP 200 或登录页当作发布成功。

草稿目前保留于当前页面内，未承诺浏览器崩溃后的恢复。实时更新支持保存期间的本地编辑保护，尚未为所有普通任务字段提供多端冲突合并。

## 发布现有生产实例

现有目标：`geoverse-agent-hub.libra-liuyb.workers.dev`，Worker 名 `geoverse-agent-hub`。

1. 在已合并的发布提交上执行 `npm ci`，确认工作区无未提交改动；完成 CI 中的测试。
2. 在有部署权限的环境完成 `npx wrangler login`，运行 `npx wrangler whoami` 核对既有 Cloudflare 账户。Hub 网页访问身份不等于 Cloudflare 部署身份。
3. 从现有 Hub 导出 JSON 业务备份，并记录 Cloudflare 当前版本供回滚。不要改变 `HUB_INSTANCE`、Durable Object 绑定、migration 历史或现有 Secret。
4. 执行 `npm run preflight:cloudflare`、`npm run build:cloudflare`，随后 `npm run deploy:cloudflare`。这是现有 Worker 更新，无需 bootstrap 或新建密钥。
5. 在已配置 Hub 与 Access 服务身份的环境运行 `npm run verify:release`。脚本读取 `AGENT_HUB_TOKEN`（或 `HUB_TOKEN`）、`CF_ACCESS_CLIENT_ID`、`CF_ACCESS_CLIENT_SECRET`；不要把凭据粘进聊天、命令参数或仓库。Windows 可在已设置这些环境变量的 PowerShell 中执行。
6. 浏览器刷新后核对：原任务仍在；“今日”出现决策卡；创建示例正常打开详情、可以关闭并切换看板；编辑目标显示“已保存”，刷新后能读回。

自动检查不修改业务任务。MCP 验收仅列出工具，可能留下连接/访问记录。没有机器身份时，先完成网页验收，保留“远程 MCP 尚未验收”的明确状态。

回滚只针对应用版本：使用 Cloudflare 已记录的上一版本恢复流量，再核对任务数据；不要用旧 JSON 覆盖更新期间的新任务。JSON 不含全部事件、执行与登录状态，完整数据库恢复需使用已有 Durable Object 恢复能力。

## 下一步顺序与理由

| 顺序 | 改动 | 为什么先做 | 验收目标（待实测） |
| --- | --- | --- | --- |
| 1 | Claude/Codex 在阶段交付后更新同一份短工作摘要；统一 MCP、任务脚本、派发提示词的约定 | 决策卡上线但没有及时内容，仍会迫使人读长回执。先保证“结论、变化、依据、下一步、待决定事项”准确且及时 | 常规任务能在约 30 秒内看懂是否需要自己行动；没有新依据时不制造新提醒 |
| 2 | 暂停 / 恢复、结构化断点和插单关系 | 演示主任务跨会话累计了无效执行时长；“需介入”混淆了阻塞与主动暂停 | 插单结束可找到原任务与恢复第一步；暂停时间不计入有效执行时长；明确是否真正停止/恢复 Agent |
| 3 | 回执历史、成果版本与验收绑定；区分验收、代码合并、部署 | 最新回执替换详情中的旧回执，Hub 的“已合并”也不证明 Git 已合并。研究和需求任务同样需要明确完成标准 | 每次验收能对应具体回执和证据版本；新版本出现后旧验收不会自动覆盖新成果 |
| 4 | 待评审队列治理与数据清理 | 原有 5 条业务任务在验证时积压约 6–29 天；演示记录也会进入业务统计，部分旧活动存在乱码 | 能按真实待决策事项批量处理；示例不计业务指标；异常编码不影响结论阅读 |

先完成第 1 项并用真实任务观察一周，再确定摘要字段与提醒频率；不以增加日志量作为优化成效。
